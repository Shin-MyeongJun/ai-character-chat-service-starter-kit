조사일: 2026-10-16 (한국 시간)

## 1. 판단과 조사 범위

**일상적인 쓰기·읽기 편의를 기본 제공하고, 장기 대화의 기억을 사용자가 확인하고 교정할 수 있게 만드는 방향을 추천한다.** 43개 유틸을 각각 별도 기능으로 옮기기보다 입력 도구, 읽기 설정, 기록 보관, 대화 정리, 기억 관리, 사용 내역 등으로 통합하는 편이 낫다.

- 외부 근거: [크랙 확프 보관소](https://chyoyam-alt.github.io/crack-userscript-archive/)의 목록 43개와 각 항목의 상세 설명을 브라우저에서 전부 읽었다. 사이트 표시는 전체 43개·모바일 37개·최근 정리 2026.08.04다. 이는 사이트의 분류이며 실제 기기별 호환성을 검증한 결과는 아니다.
- 분석 수준: 아카이브에 등록된 기능 설명을 분석했다. 스크립트 설치·실행, 43종 전체 소스 감사, 실제 크랙 계정에서의 동작·성능 검증은 하지 않았다. 설명의 ‘실시간’, ‘정확한 비용’, ‘기억력 상승’ 등을 검증된 성능으로 해석하지 않는다.
- 프로젝트 근거: 현재 작업 트리의 프런트·API·모듈 아키텍처를 읽었다. 아래 ‘기존’은 코드가 있다는 뜻이며 운영 환경 검증 완료를 뜻하지 않는다. 루트 README의 ‘프런트엔드 개발 예정’보다 실제 `apps/web` 구현과 해당 README를 우선했다.
- 우선순위는 제품 판단이다. 설치 수·활성 사용자·전환율 자료는 확인하지 못했으므로 유틸의 존재를 수요의 단서로만 본다. 특히 장기 롤플레잉 이용자의 필요가 많이 반영되었을 가능성이 있다.
- 이번 산출물은 분석 문서다. 애플리케이션 코드와 API 계약은 변경하지 않았다.

## 5. 특히 추천하는 세 가지 차별화

### A. ‘AI가 무엇을 기억하는지’ 확인하고 바로잡는 화면

자동 기억, 내가 고정한 사실, 나만 보는 메모를 구분한다. 자동 기억에는 가능한 범위에서 원문 위치와 마지막 갱신 상태를 보여준다. ‘이건 잘못 기억했어요’, ‘계속 기억해 주세요’, ‘이번 대화에서 제외’ 같은 동작을 제공한다.

기존 요약을 직접 덮어쓰면 원문 digest와 검색 벡터의 의미가 어긋날 수 있다. 제안은 자동 요약 원본과 사용자 교정/고정 사실을 분리해 저장하고, 최종 참고 정보 조합 규칙을 명시하는 것이다. 사용자 사실 간 충돌, 제작자 설정과 다른 사실의 취급, 사용 토큰 상한도 필요하다.

처음에는 내부 기억 조회를 소유권이 확인된 HTTP로 노출하는 읽기 화면부터 만든다. 사용자가 실제로 어떤 기억을 고치는지 확인한 다음 수정·고정 기능을 확장한다. 자동 응답 교정으로 매 턴 추가 LLM 호출을 붙이는 것은 나중이다.

장기 RP 이용자를 목표로 한다면 기존 memory·lorebook·prompt 기반과 가장 잘 맞는 차별화 후보다. 실제 기억 정확도 향상은 별도 대화 평가로 확인해야 한다.

### B. 답변을 버리지 않고 비교·채택하는 편집기

‘다시 생성’으로 기존 답변을 지우는 대신 후보를 보존하고 비교한다. 문단 조합은 후보 보존·선택이 안정화된 뒤 추가한다. 일반 이용자는 채택 버튼만, 고급 이용자는 문단 편집까지 사용할 수 있다.

현재 답변 API는 마지막 사용자 입력을 전제로 한다. 단순히 새 request_key를 보내서는 성공 답변의 리롤을 구현할 수 없다. 후보 그룹, 채택된 답변, 이후 문맥에 들어갈 답변, 기존 후속 메시지가 있을 때의 정책을 먼저 정의한다. 과금·모델 정보는 생성별로 보존하고 사용자가 조합한 본문은 편집본임을 구분한다.

추가 후보를 생성하는 비용과 이미 받은 문단을 조합하는 동작의 비용을 분리한다. 기억·통계·과금 기록까지 영향을 주므로 ‘편집 버튼 몇 개’ 규모로 잡지 않는다.

### C. 안심하고 오래 쓰는 기록 보관

전체 대화 내보내기, 선택한 장면 저장, 북마크, 삭제 전 영향 범위 안내를 묶는다. 다운로드한 기록을 서비스 밖에서도 읽을 수 있게 하는 것이 첫 목표다. 삭제 복원과 가져오기·이어하기는 이후 범위다.

백업 JSON에는 형식 버전, 내보낸 시각, 고정 시작 내용, 원문 순서·revision을 포함하도록 설계한다. 최초 opening/start는 일반 메시지가 아니므로 별도 포함해야 한다. 작품의 비공개 제작자 프롬프트나 로어 원문을 개인 대화 백업이라는 이유로 노출하면 안 된다.

서버 복원에는 소유권·작품/발행본 접근 가능성·ID 재매핑·요청키·생성 이력·기억 재구성이 필요하다. 이전 청구 내역을 새로운 생성으로 다시 청구하거나 복원으로 환불된 것처럼 취급하지 않는다. 먼저 읽기용 보관을 완성하면 복원 설계와 독립적으로 가치를 제공할 수 있다.

| 4 | 기억 읽기 → 사용자 교정 | 자동 기억 조회, 원문 이동, 고정 사실·교정, 재색인·충돌 처리 | 요약/임베딩 중 실패 상태 구분. 편집·되돌리기 뒤 낡은 기억 재사용 방지. 다른 사용자나 비공개 제작 자료 노출 없음. |
| 5 | 대안 답변·편집·휴지통 | 후보 보존/선택 → A/B → 문단 조합, 서버 보관/복원 | 채택 변경 후 문맥·기억 일치. 동시 생성/편집 충돌 처리. 복원 범위 명확. 생성·청구 사실 중복 없음. |
| 6 | 선택형 AI·몰입 | 집필·교정·번역·삽화·RPG 상태·환경 효과 중 수요가 확인된 것 | 명시 실행·추가 비용 안내·원본 보존·지연 측정. 매 턴 자동 호출은 효과와 비용이 검증된 뒤 결정. |

첫 구현 묶음으로는 **입력란 펼치기 + 미리보기/서식 + 템플릿 + 읽기 설정 + 시각/글자 수 + 기본 내보내기**를 추천한다. 대부분 매 턴 추가 LLM 비용 없이 체감 품질을 높인다. 그 다음 대표 기능으로 기억 조회·교정을 개발한다. 리롤 비교는 매력적이지만 데이터 계약 변경이 커서 기본 편의 묶음과 분리한다.

스타터킷으로 제공할 때는 운영자가 기능을 선택할 수 있어야 한다. 기본 편의·기록 내보내기는 기본 제공 후보, 기억 교정·리롤은 활성화 가능한 확장 후보, 번역·삽화·집필은 공급자/요금 설정이 필요한 선택 기능으로 나누는 것을 제안한다. 처음부터 독립 배포 서비스로 분리할 필요는 없으며, 기존 모듈 경계를 유지한 기능 설정으로 시작할 수 있다. 운영자가 별도 외부 스크립트를 안내하지 않고도 이용자에게 완성된 사용 흐름을 제공한다는 점이 스타터킷의 판매 가치가 될 수 있다.

## 7. 구현 시 프로젝트 구조에 연결하는 원칙

[모듈 아키텍처 및 명명 규칙](../references_document/reference/module-architecture-and-naming.md)을 따른다. 아래는 제안이며 새 모듈명이나 HTTP 경로를 확정한 것은 아니다.

- 읽기·작성 UI는 프런트 책임으로 두고, 계정 동기화가 필요한 설정만 서버에 저장한다. 현재 채팅 페이지에 기능을 전부 누적하지 말고 작성란·본문 렌더러·설정·메모 패널을 역할별로 분리한다.
- 대화 제목·핀·보관 등 대화의 사용자 설정은 conversation에, 메시지 후보·선택·편집 이력은 chat에 책임을 둔다. 개인 즐겨찾기/폴더/템플릿은 콘텐츠 공개 태그와 분리된 소유 범위를 설계한다.
- 자동 기억·사용자 기억 정책은 memory, 제작자 로어와 활성화는 lorebook, 최종 조합은 prompt의 기존 경계를 유지한다. 여러 모듈의 실행 순서와 트랜잭션은 기존 workflow 또는 최상위 use case에서 조율한다.
- 비용 화면은 chat의 생성 사실, billing의 청구/사용량, credit의 지갑·원장을 공개 service/types로 조합한다. 모듈 간 repository·ORM 직접 참조를 추가하지 않는다. reporting에는 지갑 쓰기나 생성 복구를 넣지 않는다.
- 실시간 모델 상태는 자체 관측 데이터가 필요하다. 저장된 latency, 완료 시각, 오류 분류가 있다는 사실만으로 실시간 모델 품질 점수나 TPS가 완성되지는 않는다.
- 신규 공개 조회/명령은 소유권·최신 활성 사용자·revision을 확인한다. 책임이나 공개 인터페이스가 바뀌면 해당 모듈 ARCHITECTURE.md를 갱신한다.
- 유틸의 네트워크 가로채기·DOM 추측·내부 API 강제 수정 방식을 이식하지 않는다. 네이티브 서비스는 안정적인 ID와 명시적 공개 계약으로 구현할 수 있다. 라이브러리/스크립트 코드를 가져오는 단계에서는 해당 코드의 라이선스를 별도로 확인한다.

## 8. 효과를 판단할 지표

| 목적 | 관찰할 지표 | 해석 시 주의 |
| --- | --- | --- |
| 쓰기 편의 | 긴 초안 전송 완료율, 초안 복구 성공, 템플릿/미리보기 사용 후 전송 | 사용 횟수만으로 만족도나 전송 품질을 단정하지 않는다. |
| 장기 대화 | 긴 대화 재방문, 기억 오류 신고·교정 빈도, 교정 후 같은 오류 재발 | 기억 기능을 많이 쓰는 사람이 원래 오래 사용하는 집단일 수 있다. |
| 답변 선택 | 후보 생성 대비 채택, 비교 후 대화 지속, 채택까지 비용/시간 | 리롤 증가를 품질 개선으로 해석하지 않는다. |
| 비용 신뢰 | 비용 표시와 청구 기록 일치, 비용 관련 문의, 내역 재조회 성공 | 예약·해제·확정·환불을 구분해 비교한다. |
| 기록 보존 | 내보내기 완전성, 북마크 재방문, 실수 삭제·복원 성공 | 채팅 본문 자체를 분석 로그에 수집할 필요는 없다. |

우선은 소규모 이용자에게 기본 편의 묶음과 기억 조회 화면을 제공해 관찰한다. 아카이브의 추천순이나 기능 수를 제품 우선순위의 유일한 기준으로 삼지 않는다.

## 9. 후순위로 두는 이유

- 번역을 거쳐 비용을 절약한다는 가설은 언어별 토큰 차이뿐 아니라 번역 호출비·지연·설정 보존·문체 품질까지 측정해야 한다. 현재 가격 정책에서 절약이 보장되지 않는다.
- 삽화·RPG HUD는 특정 작품에서 효과가 클 수 있으나 새 생성 작업·상태 모델·비용 구조가 필요하다. 이미지 저장 기반이 있다고 이미지 생성 기능도 완성된 것은 아니다.
- 배경·날씨·환경음은 선택형 몰입 요소로 검토하되 기본 읽기 품질보다 먼저 하지 않는다.
- 보관함 복구기·랭킹 제거기는 특정 서비스의 결함이나 UI 선택에 대한 보완이다. 기능 이름을 이식하기보다 정상적인 목록·정렬·표시 설정으로 해결한다.
- 모든 기능을 기본 켜기보다 글쓰기 도구·기억·기록·비용으로 진입점을 통합하는 편이 초기 이용자에게 이해하기 쉽다.
