## 5. 채팅 연동의 필수 계약

1. 사용자 메시지를 저장하고 반환된 message_id/revision을 답변 요청에 사용한다.
2. 답변 요청은 request_key와 참여자 product_character_id를 포함한다. 한 논리 요청의 본문과 키를 유지한다.
3. `202 pending`은 실패로 표시하지 않고 Retry-After에 따라 같은 요청으로 상태를 확인한다. 서버에 없는 GET 상태 API를 가정하지 않는다.
4. `503 storage_pending_recovery`는 새 생성 요청으로 바꾸지 않고 같은 키로 복구한다. `503 billing_not_configured`와 구분한다.
5. 정상 응답 뒤 저장된 메시지를 다시 동기화하고 UI의 임시 표시와 중복하지 않는다. 새로고침 후 미완료 요청을 복구할 수 있도록 비밀정보를 제외한 요청 식별자를 사용자별로 보관하고 로그아웃 시 정리한다.
6. 입력 실패와 답변 실패를 분리한다. 이미 저장된 사용자 메시지를 답변 재시도 때문에 다시 생성하지 않는다. 결과가 불확실한 메시지 저장에는 조회·대조 또는 추가 멱등 계약이 필요하다.
7. 잔액 부족·세션 만료·속도 제한·모델 이용 불가·요약 대기는 각각 사용자 행동을 안내한다. 오류 응답 형식 차이는 API 클라이언트에서 정규화한다.
8. 현재 비스트리밍 계약을 사용해 생성 중 표시 후 완성된 답변을 보여준다. SSE와 실제 생성 취소 기능은 후속으로 둔다.
9. Access 만료 시 Refresh 쿠키도 지우는 현재 정책을 고려해 세션 부트스트랩/갱신 순서를 결정한다. 모든 401을 일반적인 자동 refresh로 처리하지 않는다. 다중 탭 갱신을 직렬화한다.
10. 콘텐츠 변경·되돌리기는 서버의 리비전·무효화 계약에 따른다. 과거 대화에 최신 작품 업데이트를 UI가 임의로 적용하지 않는다.

## 6. 구현 구조 제안

기존 저장소의 Next.js·React·TypeScript·lucide-react·openapi-typescript 기반을 사용한다. 이번 계획에서 라이브러리 추가나 버전 변경은 하지 않는다.

```text
apps/web/
  app/                  # URL, 레이아웃, 페이지 조립
  features/
    auth/               # 쿠키 세션 상태와 인증 화면
    catalog/            # 홈, 탐색, 작품 상세
    chat/               # 메시지, 입력, 답변 상태와 복구
    account/            # 내 정보, 잔액
    studio/             # 2차 제작 화면
  components/ui/        # 버튼, 입력, 다이얼로그, 카드, 상태 표시
  lib/api/              # 생성 타입, HTTP/CSRF, 오류 변환
  styles/               # 색·간격·타이포 토큰
```

- 화면 컴포넌트 안에 원시 API 호출을 흩어놓지 않는다. 서버 응답과 카드/대화 표시 모델을 구분한다.
- 시각 초안용 fixture와 실제 API 모드는 명시적으로 분리한다. 실제 연동 실패 시 가짜 성공 데이터로 대체하지 않는다.
- 우선 동일 출처의 프런트/API 구성을 목표로 한다. 프록시 도입 시 `/auth` 콜백·Origin·Set-Cookie 전달을 함께 맞춘다. 다른 출처로 실행하면 기존 CORS와 CSRF 허용 출처를 정확히 연결한다.
- JWT를 localStorage에 저장하지 않고 HttpOnly 쿠키 인증 계약을 유지한다.

## 7. 진행 단계

### A. 화면 골격과 디자인 확정

홈 → 상세 → 시작 선택 → 채팅 → 내 대화를 샘플 데이터로 연결한다. 모바일과 PC 레이아웃, 카드·본문·입력·빈 화면·오류 표시까지 포함한다. 이 단계는 시각 프로토타입이며 실제 플레이 완료로 표시하지 않는다.

### B. 실제 작품 하나로 세로 연결

인증, 기존 발행 작품 상세, 대화 생성, `/start`, 메시지 저장, 답변 생성을 연결한다. 가격 설정·모델·테스트용 지갑 및 크레딧·필요한 워커를 준비한다. 이 단계부터 실제 사용을 시작한다.

### C. 다시 방문해서 사용할 수 있게 만들기

내 대화 목록, 공개 카탈로그, 상세 표시 정보, 잔액 조회를 최소 구현한다. 새로고침·이동 후 복귀·오류 복구·입력 초안 보존을 완성한다. 이 단계 종료가 실사용 프로토타입의 기준이다.

### D. 제작 흐름

내 작품 → 기본 정보 → 캐릭터·로어북 선택 → 시작 설정·모델 → 미리보기 → 발행을 기존 backend 계약으로 연결한다. 변경을 즉시 공개하지 않고 초안과 발행 버전을 구분한다. 초기는 캐릭터 하나로 단순화하되 데이터 모델은 다중 참여자 구조를 유지한다.

### E. 실사용 피드백으로 개선

관찰 항목은 대화 시작 성공 여부, 답변 대기 시간, 중복 표시·중복 차감 여부, 재진입 복원, 긴 대화 기억 품질, 모바일 입력과 가독성이다. 로그에는 메시지 원문 대신 요청 식별자·오류 코드·시간 등 필요한 진단 정보만 남긴다.

메모리 종료 사유 검증은 장기 대화 품질 평가 전 보강한다. 스트리밍, 모델 선택, 추천답변, 기억 편집, 대화 분기 등은 실제 사용에서 우선순위를 정한다.

## 8. 1차 제외 범위와 완료 조건

1차 제외: 실결제, 자동 충전, 댓글·팔로우·후원, 개인화 추천 엔진, 복잡한 랭킹, 파티챗, 이미지 생성, 관리자 콘솔, 네이티브 앱. 도움말에서 확인한 부가 기능을 전부 구현 목표로 삼지 않는다.

실사용 프로토타입 완료 조건:

- 실제 계정으로 작품을 선택하고 시작 설정을 골라 대화한다.
- 답변과 차감 상태가 서버에 저장되고, 실패 시 다음 행동을 알 수 있다.
- 새로고침과 다음 날 재방문 후 내 대화에서 이어갈 수 있다.
- PC와 휴대폰에서 입력·스크롤·읽기가 가능하다.
- 샘플 화면과 실제 연동 화면이 혼동되지 않고 미구현 동작을 성공한 것처럼 표시하지 않는다.

계획 단계의 기본 선택: 모바일 우선 반응형, 작품 중심 탐색, 비스트리밍 실제 채팅 우선, 제작 화면은 두 번째 묶음. 서비스명·브랜드색·캐릭터 이미지 스타일은 A 단계에서 확정한다.
