# 상품 구현 작업 목록

작성일: 2026-09-08

상태: 구현 전 계획. 2026-09-08 추가 지침 반영. 사용자 확정 사항과 구현 제안/미정 사항을 구분한다. 아래 테이블명과 커밋 경계는 제안이며, 실제 코드 변경·마이그레이션·커밋은 아직 수행하지 않았다.

## 1. 범위와 합의한 원칙

### 구현 진행 기록

- 선행 정리: `cd8575e` (모듈 이동 및 계획 문서).
- C01 완료: 소유자 전용 작업본 CRUD, 트랜잭션·입력 검증, 미설정 인증 503. 전체 178 tests 통과. HTTP 인증/세션은 기존 character와 동일하게 앱 조립 시 주입한다.
- C02 구현 완료: 소유권·대상 범위 검증, 같은 상품 복합 FK, Alembic 기반과 PostgreSQL 통합 테스트 추가. 179 passed / DB 2 skipped(엔진 준비 중).
- C03~C14 대기. 다음: start_set 유형.
- DB 실검증 환경: Docker 엔진 시작 전에는 연결 불가. 테스트 DB 준비 중이며 운영 DB 변경 없음.
- 기본 결정: 기존 상품 테이블을 작업본으로 사용. 만료 후 생성 중지·기억 보존. LLM은 제작자 허용 범위를 넘지 않음. 알림 전송은 향후 alarm 모듈.

- 상품은 캐릭터 최소 1개, 대표 캐릭터 1개, 지정 LLM과 추론 설정, 첫 메시지, 시작 설정 최소 1개를 갖춰야 발행할 수 있다.
- 여러 캐릭터·로어북을 포함한다. 초기 실행은 상품의 LLM 하나가 여러 캐릭터를 연기하는 방향이다.
- 원본 편집은 상품 업데이트가 아니다. 제작자가 발행할 때만 새 상품 버전을 생성한다.
- 발행 시 내용·구성·관계·실행 설정을 고정한다. 기존 고객 대화는 사용 중인 버전을 참조한다.
- 버전별 패치노트가 필요하다. 에셋 추가·기본 이미지 변경만 있는 업데이트는 제작자가 자동 적용 또는 고객 선택을 정한다. 캐릭터·로어북 내용 변경은 고객 선택이 필수다.
- 구버전 만료 정책은 product_snapshots의 운영 컬럼에 저장한다. 관리 영역이 설정하고 상품·대화 영역이 적용한다. 유예기간 이후에도 대화 기억은 유지한다. alarm 모듈 구현은 향후 범위다.
- LLM 지원 중단은 양측에 안내하며 같은 제공자와 유사한 추론 설정을 우선해 대체한다. 상품에 제작자 지정 대체 범위·대체 불가 정책을 둔다. 공지 시점부터 종료 24시간 전까지 전환을 준비/적용한다. 세부 예외는 6절 참고.
- 사용·결제 통계는 별도 집계 테이블로 관리한다. 과금 계산은 billing 소관이다.
- 로어북 간 관계는 이번 범위에서 보류한다. 향후 로어북 에셋의 실제 CRUD도 별도 작업이다.

## 2. 현재 구현 상태

저장소의 SQLAlchemy 모델과 초기화 SQL을 기준으로 확인했다. 실행 중인 DB에 실제 적용된 상태는 확인하지 않았다.

- `products`, `product_characters`, `product_lorebooks` 모델이 있다. 상품 서비스·라우터 등은 빈 파일이다.
- 대표 캐릭터의 최대 1개 제약은 있다. 발행 시 최소 1개 캐릭터와 대표 캐릭터 존재 검증은 별도 구현이 필요하다.
- `product_snapshots`, `character_snapshots`, `lorebook_snapshots`와 상품 스냅샷 구성 연결 테이블이 이미 있다. `ProductSnapshot`을 발행 버전으로 사용하므로 별도 `product_versions`를 중복 생성하지 않는다.
- 스냅샷은 `snapshot_data` JSONB를 사용한다. 기존 README에 이미지·에셋 포함 의도는 있지만, 구체적인 payload 계약과 발행 기능은 없다. 이미지·에셋 전용 컬럼이 없다는 것이 저장 자체가 불가능하다는 뜻은 아니다.
- 상품 캐릭터 ↔ 상품 로어북 대상 연결, 시작 설정, 패치노트, 대화 버전 고정은 없다.
- `conversations`, `conversation_characters`, `messages`는 현재 원본 상품·캐릭터 중심이다.
- `usage_logs`, `credit_transactions`, `payments`는 있다. 상품·버전별 집계 및 결제 귀속 계약은 추가해야 한다.
- 초기화 SQL만 수정해도 기존 DB가 갱신되지는 않는다. 각 스키마 변경은 기존 DB용 마이그레이션과 신규 DB용 정의를 함께 다룬다.

## 5. 기능별 커밋 계획

각 행은 하나의 검토 가능한 커밋 단위다. 해당 기능의 모델·마이그레이션·서비스·관련 테스트를 함께 포함한다. 작업량이 커지면 스키마와 기능을 나누되, 매 커밋에서 기존 테스트가 통과하도록 한다. 아래 메시지는 계획이며 실제 커밋 생성 지시가 아니다.

| C09 | `feat(product): expose update notices` | 최신/현재 버전 비교, 패치노트·적용 정책 조회 계약. alarm 전송은 제외 | 조회 일관성, 타 사용자 대화 정보 차단 |

| C11 | `feat(governance): manage version availability` | 스냅샷 운영 컬럼의 유예·만료 정책, 상태 조회, 대화 이용 가능 여부 검사 | 만료 경계 시각, 정책 변경 이력, 스냅샷 물리 삭제와 구분 |
| C12 | `feat(llm): handle model retirement and replacement` | 제작자 지정 정책과 지원 중단 대응, 양측 조회 계약, 실행 모델 해석 | 원래 설정 보존, 실제 모델 기록, 대체 불가 처리 |
| C13 | `feat(usage): attribute usage to product versions` | 사용 이벤트 상품/버전 귀속, 멱등성, billing 결제/환불 귀속 인터페이스 | 재시도 중복 방지, 대화 전환 후에도 과거 귀속 유지 |
| C14 | `feat(product): aggregate usage and payment statistics` | 일별 상품/버전 집계와 제작자 조회, 재집계 | 중복·환불·지연 이벤트 처리, 고유 이용자 중복 제거 |

의존 순서: C01 → C02 → C03 → C04 → C05 → C06 → C07 → C08 → C09 → C10. C11은 C08~C09, C12는 C04/C08 및 안내 계약, C13은 C08, C14는 C13에 의존한다. 세부 구현 순서는 지침 추가 후 조정한다.

모든 DB 변경 커밋에서 신규 DB 생성과 기존 DB 업그레이드를 검증한다. PostgreSQL 고유 제약·FK·트랜잭션 동작은 DB 통합 테스트로 확인하며, 구조를 그대로 복제하는 테스트보다 발행/전환의 실제 불변 조건을 검증한다.

## 6. 추가 지침 반영과 남은 결정

### 6.1 사용자 확정 사항

- 본인 소유 캐릭터·로어북만 포함한다. 연결 시와 발행 시 모두 소유권을 확인한다.
- 시작점 후보는 여러 개지만 대화 생성 시 정확히 하나를 선택한다. 하나뿐이면 그 항목을 적용한다.
- 패치노트는 첫 발행부터 필수이며 발행 후 오타 수정은 허용한다.
- 기본 이미지 변경은 에셋 추가와 같은 적용 정책을 사용한다. 캐릭터/로어북 본문 변경이 함께 있으면 고객 선택이 우선한다.
- 유예기간 이후에도 기억을 유지한다. 기억 보존이 만료 버전의 계속 실행을 의미하지는 않는다.
- 만료 정책은 상품 스냅샷에 저장하고 alarm 모듈은 향후 별도 구현한다.
- 이미지·에셋은 JSON에 넣지 않고 스냅샷 자식 테이블에 저장한다. 실제 바이너리는 저장소에 두고 불변 참조만 저장한다.
- 제작자가 상품 설정에서 LLM 대체 범위와 대체 불가 정책을 지정한다. 대체 후보가 없으면 동일 모델 계열의 다른 버전을 우선 검토한다.
- 제공사의 종료 공지 시점부터 종료 1일 전까지 대체를 준비/적용한다.

### 6.2 충돌을 피하기 위한 설계 제안

- 작업본 질문은 답변이 비어 있으므로 미확정이다. 기존 products/연결 테이블을 작업본으로 쓰고 고객은 스냅샷만 읽는 기존 제안을 유지한다.
- 스냅샷 불변 대상은 콘텐츠·구성·실행 설정과 자식 행이다. expires_at 등 운영 컬럼은 권한 검사와 변경 이력을 통해 수정 가능하게 한다.
- 패치노트는 버전과 1:1인 product_release_notes로 분리하는 것을 제안한다. 오타 수정은 이력을 남기고 실행 내용·적용 정책을 변경하지 않는다. 오타인지 의미 변경인지 자동으로 완벽히 판별할 수는 없다.
- 같은 모델 계열은 이름 문자열 추측 대신 등록된 model_family 식별자로 관리한다. 제공 회사가 같다는 것과 같은 모델 계열이라는 것은 다르다.
- 동일 계열 다른 버전도 제작자가 허용한 범위 안에서 우선 검토하는 해석을 제안한다. 허용 범위를 벗어난 대체는 자동 수행하지 않는다. 사용자가 말한 최후 대체가 범위 제한을 넘는 예외인지는 미확정이다.
- 공지 등록 시 후보 선정과 전환 예약을 시작하고 종료 24시간 전까지 완료하는 기본안을 제안한다. 공지가 늦거나 후보가 없으면 지연 사실을 기록하고 제작자의 대체 불가 정책을 적용한다. 아직 공지가 없는 날짜를 추측하지 않는다.
- 동일 계열도 사용 가능한 버전이 전혀 없을 수 있으므로 최종 정책이 필요하다. 정책 선택값은 아직 미확정이며, 안전한 기본 제안은 신규 생성 중지·기록과 기억 보존이다.
- 버전 만료만으로 기억을 삭제하거나 고객을 강제 전환하지 않는 안을 제안한다. 미동의 시 신규 생성 중지와 버전 선택 안내를 제공하되, 정확한 동작은 추가 확정한다.

### 6.3 위임받은 통계 기본 설계

- 저장 시각은 UTC, 집계 일자는 Asia/Seoul 기준이다. 일자 경계는 시간대 변환 후 계산한다.
- 사용 횟수는 고객에게 저장 완료된 AI 응답 턴 수다. 다중 캐릭터 메시지는 동일 턴이면 1회, 실패·취소·재시도는 별도 운영 수치이며 중복 성공 처리하지 않는다.
- 이용자는 기간 내 성공 응답이 있는 고유 사용자다. 대화 수·메시지 수·생성 턴 수는 별개로 집계한다.
- 요청별 토큰/비용은 실제 제공사 사용 기록 기준으로 남긴다. 실패한 요청에도 실제 비용이 발생하면 성공 턴 통계와 분리해 비용에 반영한다.
- 결제 횟수/금액은 상품에 명시적으로 귀속된 성공 거래만 집계한다. 크레딧 사용량과 현금 매출을 구분하고, 충전/구독 결제를 임의 배분하지 않는다. 통화별로 분리하며 refund는 원거래 버전에 귀속한다.
- 1시간마다 증분 집계하고 매일 전일까지 최근 7일을 재집계한다. 그보다 늦은 환불/정정도 원거래 집계일을 재계산하도록 변경 일자 큐를 유지한다.
- 일별 고유 이용자 수를 합산하지 않는다. 기간별 고유 이용자는 사용자별 활동 사실에서 DISTINCT로 계산한다.
- 추가 제안 테이블: product_user_daily_activity(일자·상품·사용자), product_version_user_daily_activity(일자·버전·사용자), 집계 체크포인트/재집계 대상 일자. C13~C14에 포함한다.
- 기술 기본 보존안: 상세 분석 이벤트 90일, 사용자별 일별 활동 및 일별 집계 24개월. 기간 전체 재집계를 위해 보존 기간 내 필수 집계 근거를 유지한다. 삭제 기능은 별도 구현 전까지 자동 실행하지 않는다. 대화/기억과 billing 원장의 보존은 이 분석 정책으로 삭제하지 않는다.

### 6.4 위임받은 마이그레이션 기본 설계

- Alembic 기반의 추가 → 백필 → 검증 → 제약 강화 순서로 진행한다. 신규 초기화 SQL과 최종 모델도 일치시킨다.
- 적용 전 실제 DB 데이터 수·제약·기존 스냅샷 유무를 조사한다. 기존 데이터가 없다고 가정하지 않는다.
- 초기에는 새 FK를 nullable로 추가한다. 기존 버전이 명확한 데이터만 백필하고 처리 건수와 미해결 건수를 남긴다.
- 당시 내용을 입증할 수 없는 대화는 현재 원본으로 과거 스냅샷을 만들지 않는다. legacy 미해결 상태로 보존하며 원본과 기억은 삭제하지 않는다.
- 미해결 데이터가 있으면 전체 NOT NULL 강화를 보류하거나 신규 행에만 필수 조건을 적용한다. 과거 대화 실행 전환은 검증 가능한 기준이 생길 때 별도 수행한다.
- 변경 전 백업과 복원 절차를 검증하고, 실제 데이터에 파괴적 다운그레이드/자동 삭제는 하지 않는다.
