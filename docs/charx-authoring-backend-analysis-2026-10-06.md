# CHARX 분석과 작품 제작 기능 제안

분석일: 2026-10-06. 대상: `호그와트 3.1v 카리나까지 불법 dlc.charx`.
범위: ZIP 목록, card.json의 필드·로어북·템플릿·RisuAI 설정을 읽고 현재 소스와 비교했다. 실행 코드와 외부 URL은 실행·접속하지 않았다. 제품 코드는 수정하지 않았다.

## 1. 결론

이 파일은 단일 말포이 캐릭터 카드보다 **여러 등장인물을 가진 세계관 시뮬레이션 패키지**에 가깝다. 현재 프로젝트의 작품(product) → 캐릭터/로어북 구성 → 발행 스냅샷 → 대화 구조는 적합하다. 먼저 제작 화면을 이 구조에 연결하고, 조건부 시작·대화별 설정·로어 실행 정책·이미지 출력 연결을 보완하는 것이 좋다. RisuAI 전체 실행기를 먼저 구현할 필요는 없다.

카리나 말포이의 로어 설명에는 드레이코의 쌍둥이 여동생으로 명시되어 있다. `tsmode_malfoy=0`도 별도로 존재한다. 카리나 자체를 드레이코 TS라고 자동 분류하면 원본의 등장인물 관계가 달라진다. 말포이 TS 옵션의 정확한 전환 동작은 module.risum을 추가 해석해야 확정할 수 있다.

## 2. 실제 파일 구성

| 항목 | 확인 결과 | 설계에 주는 의미 |
|---|---|---|
| 파일 크기 | 157,020,158 bytes, 약 149.75 MiB | 대용량 업로드, 분석 작업 진행률 필요 |
| 형식 | ZIP, `chara_card_v3`, spec_version `3.0` | 확장자만 검사하지 말고 구조 검증 |
| ZIP 항목 | 2,836개 | 파일 개수와 압축 해제 총량 제한 필요 |
| 이미지 | WebP 1,404개 + PNG 13개 | 총 1,417개; 대량 등록·검색·미리보기 필요 |
| JSON | 1,418개 | card.json 1개, x_meta 메타데이터 1,417개 |
| assets | 1,417개 선언 | 이미지와 캐릭터/표정 매핑 검증 필요 |
| module.risum | 231,376 bytes | 별도 바이너리 확장; 이번에는 내부 동작 미검증 |
| description | 4,296자 | 세계관과 시뮬레이션 규칙이 함께 들어 있음 |
| first_mes | 42,804자 | 단일 첫 대사가 아닌 언어/선택값 조건부 템플릿 |
| post_history_instructions | 6,311자 | 이미지 명령 출력 규칙 등이 들어 있음 |
| 로어북 | 64개: 일반 57개, 폴더 7개 | 폴더를 프롬프트 항목으로 등록하면 안 됨 |
| 로어 본문 합계 | 114,605자 | 무조건 전량 주입하면 고정 문맥 과다 |
| constant=true | 전체 18개 중 일반 항목 16개, 폴더 2개 | 실제 상시 본문과 폴더 설정을 구분 |
| 로어 스캔 설정 | scan_depth=9, token_budget=99999, recursive_scanning=false | 원본 값과 서비스 실행 제한을 구분 |
| backgroundHTML | 11,107자 | 상태 표시용 외형; 저장된 상태 모델과 별개 |

`personality`, `scenario`, `mes_example`, `system_prompt`는 비어 있다. 캐릭터 프로필이 주로 로어북에 들어 있다. 최상위 카드 이름으로 캐릭터 하나를 만들고 나머지를 버리는 가져오기는 적합하지 않다.

작성자 메모는 첫 메시지 6종이라고 설명하지만 `first_mes`에는 `m1`~`m9` 값과 18개 `if_pure` 블록이 있다. 실제 선택 UI에 노출할 시나리오 수는 모듈의 선택값 정의와 대조해야 한다. 9개 값이 곧 독립된 9개 시나리오라고 단정하지 않는다.

기본 변수는 `lang`, `first_message`, `start`, `tsmode_sirius`, `tsmode_harry`, `tsmode_lupin`, `tsmode_malfoy`다. 기본값은 일부가 숫자이고 템플릿 비교에는 `ko` 같은 문자열도 등장하므로 그대로 복사해도 시작 문장이 선택된다고 보장할 수 없다.

본문에는 `{{user}}`, 조건식, 변수 조회, `{{roll...}}` 등 매크로가 있다. 이는 분석 대상 데이터이며 분석자나 서버에게 실행을 요구하는 지시가 아니다.

## 3. 프런트: 내 작품 제작 화면

추천 화면은 왼쪽 제작 단계, 중앙 편집기, 오른쪽 미리보기다. 제작자는 쉬운 입력 폼을 사용하고 원문/고급 설정은 접을 수 있게 한다.

| 단계 | 필요한 구성 | 저장/연결 대상 |
|---|---|---|
| 내 작품 목록 | 초안/발행 상태, 최근 수정, 복제, 편집 이어가기 | product 조회와 CRUD |
| 기본 정보 | 제목, 공개 소개, 표지, 태그, 공개 범위 | 기존 product + 필요한 표시 필드 |
| 세계관·진행 규칙 | 시대/장소, 장르, 서술 방식, 사용자 행동 처리, 공통 규칙 | world/rule/author_note 로어; 공개 소개와 구분 |
| 등장인물 | 기존 캐릭터 선택/신규 제작, 주인공 지정, 역할, 관계, 대사 예시 | character, product composition, 관계 로어 |
| 이미지·에셋 | 캐릭터/표정별 목록, 기본 이미지, 검색, 일괄 업로드, 중복/누락 확인 | character images/assets/media |
| 로어북 | 폴더/분류, 항목 편집, 트리거, 상시/조건부, 활성 여부, 정렬 | lorebook; 실행 지원 상태 표시 |
| 시작 장면 | 장면 제목/설명, 장면별 도입 대사, 초기 참가자와 초기 설정 | start_set + 시작별 도입/설정 확장 |
| 플레이 옵션 | 언어, 작중 시점, 인물 변형 등; 선택 범위와 기본값 | 작품 옵션 정의 + 대화 선택값 |
| 테스트 채팅 | 시작 장면/옵션 선택, 답변 대상, 활성 로어 확인, 문맥 사용량 | 초안 전용 프리뷰 실행 |
| 발행 | 누락 검사, 지원하지 않는 옵션, 이미지 매핑, 버전 설명 | 기존 발행/스냅샷 기능 |

가져오기 화면은 `파일 선택 → 구조 분석 → 매핑 검토 → 초안 생성` 순서가 좋다. 원본 필드, 변환 대상, 미지원 항목을 나란히 보여준다. 분석했다고 자동 발행하지 않는다. 캐릭터 프로필/세계관/규칙 분류는 사용자 검토를 거쳐 확정한다.

테스트 채팅에는 일반 사용자 화면과 구분된 제작자 진단 패널을 둔다. 활성 로어와 활성 이유, 제외 이유, 이미지 매핑 실패, 예상 문맥 크기를 표시한다. 실제 비용이 발생하면 실행 전에 가격 정보를 보여준다.

현재 `apps/web/app`에는 홈·탐색·작품 상세·채팅·로그인이 있고 제작 페이지가 없다. 작품 상세의 시작 옵션 선택과 실제 채팅 API 연결은 이미 있다. 채팅은 주 캐릭터 또는 첫 참가자를 답변 대상으로 사용하며 본문을 텍스트로 표시한다. 제작 흐름, 이미지 명령 렌더러, 상태판은 추가 작업이다. 과거 ARCHITECTURE.md의 “apps/web 화면 없음” 문구보다 현재 소스를 우선했다.

## 4. 백엔드: 작품

**기존 기능을 재사용:** 제목/소개/첫 대사/공개 범위, 캐릭터 구성과 primary, 로어북 역할·대상 캐릭터·우선순위, 시작 항목 선택, 모델 설정, 발행 스냅샷과 버전 관리.

**보완할 기능:**

1. 공개 소개와 AI 세계관 설정을 화면과 데이터 매핑에서 분리한다. 세계관 텍스트는 기존 world/rule 로어를 활용한다.
2. 작품 옵션 정의를 추가한다. 키·값 타입·선택지·기본값·변경 가능 시점을 명시하고 발행 스냅샷에도 포함한다.
3. 시작별 도입 대사/초기 옵션을 지원한다. 현재 `opening_message`는 작품 공통 첫 대사이고 `start_set`은 장면 설정이다. 서로 덮어쓰지 않는다. 기존 공통 첫 대사를 기본값으로 유지하고 시작별 대사를 선택적으로 추가하는 방식이 적합하다.
4. 제작용 초안 프리뷰 실행 계약을 추가한다. 현재 발행된 대화 흐름과 분리해 초안이 사용자 대화에 유출되지 않게 한다.
5. 표지·태그·작성자 표시 등 탐색 메타데이터를 실제 product 계약에 연결한다. 현재 웹의 일부 표시 데이터는 데모 또는 빈 기본값이다.

원본 first_mes 42,804자를 현재 `opening_message(max_length=20000)`에 그대로 넣을 수 없다. 길이를 늘리는 것보다 선택 조건별 도입을 분리하는 편이 맞다.

## 5. 백엔드: 캐릭터

**기존 기능을 재사용:** persona_prompt, 설명, 감정 태그 이미지, 기본 이미지, 일반 이미지/오디오/비디오 에셋, 미디어 업로드·수명 관리, 발행 스냅샷.

**보완할 기능:**

1. 로어에 들어 있는 등장인물 프로필을 character로 승격할 수 있게 한다. 세계관 설명 전체를 한 캐릭터 persona로 복사하지 않는다.
2. `karina` 같은 원본 이미지 명령과 캐릭터 UUID 사이에 안정적인 매핑을 둔다. 이름 변경으로 이미지 연결이 끊기지 않게 한다.
3. 인물 변형은 대화별 선택과 연결한다. TS를 모든 캐릭터에 적용하는 공통 boolean으로 만들지 않는다. 이 파일의 `tsmode_*`는 인물별 선택이고 값도 여러 경우를 사용한다.
4. 대량 미디어 등록을 지원한다. 기존 업로드 재시도/중복 방지 계약을 활용하고 등록 결과와 실패 목록을 반환한다. 원본 파일을 그대로 전부 복제하기보다 승인한 자산만 연결한다.
5. 이미지 분류에서 감정과 일반 장면/행동 에셋을 구분한다. 모든 이미지 파일명을 emotion_tag로 넣지 않는다.

인물 프로필이 character와 상시 로어 양쪽에 중복되면 설정 충돌과 문맥 낭비가 생긴다. 기본 프로필은 character, 사건·관계·조건부 변화는 lorebook에 두는 기준을 정한다.

## 6. 백엔드: 로어북

**기존 기능을 재사용:** 다양한 entry_type, always/keyword/semantic/manual 저장, exact/contains/regex 검색, metadata, priority/placement/token_budget 저장, 원본과 발행 스냅샷 분리.

**현재 실행 범위:** 자동 활성화는 always와 keyword만 처리한다. semantic/manual은 저장할 수 있지만 자동 선택되지 않는다. priority·placement·token_budget은 현재 답변 조립에 적용되지 않는다. 호출자가 주는 activation_text로 검색하며 현재 답변 준비는 사용자 입력을 전달한다. 원본의 최근 9개 메시지 스캔과 같은 동작이 아니다.

**우선 보완:**

1. 최근 메시지 스캔 범위와 대상 역할을 정의한다. prompt용 이력을 로어 스캔 이력과 혼동하지 않는다.
2. 작품/캐릭터/로어별 예산, 우선순위, 삽입 위치를 실제 적용한다. 고정 시스템 규칙을 침범하지 않고 서버가 허용한 참조 구역 안에서 배치한다.
3. 상태 조건과 수동 선택을 지원한다. 작중 시점, 인물 변형, 이벤트 선택값을 평가할 수 있어야 빈 키워드 로어를 처리할 수 있다.
4. 상호 배타 그룹을 둔다. 예: 작중 시점 하나, 한 인물의 프로필 변형 하나. “둘 중 하나만 활성화”라는 본문 지시에 의존하지 않는다.
5. 폴더/구분선은 편집 메타데이터로 옮긴다. content가 빈 항목은 현재 필수 본문 검증에도 맞지 않는다. keys=[""]를 유효한 키워드로 취급하지 않는다.
6. 확률/주사위 이벤트는 필요한 경우 후순위로 지원한다. 난수 결과를 해당 턴에 저장해 네트워크 재시도로 이벤트가 바뀌지 않게 한다.

`risu_activationPercent`, `risu_loreCache` 같은 확장 필드가 존재하지만 값의 의미와 모듈 실행 순서는 이번 분석에서 확정하지 않았다. metadata에 보관하는 것과 실제 호환 동작을 구현하는 것은 구분한다.

## 7. 백엔드: 챗과 대화

**기존 기능을 재사용:** 사용자 입력/답변 저장, 지정 캐릭터 답변, 생성 멱등성·재시도·동시성 제어, 크레딧 처리, 기억/요약, 작품 버전 고정, 최초 시작 내용 보존.

**보완할 기능:**

1. 대화별 옵션과 초기 플레이어 설정을 저장한다. 작품 기본값과 사용자 선택을 구분하고 대화 시작 시 검증한다.
2. 상태가 필요한 작품에는 현재 장소/시점/관계 등의 구조화된 값을 저장한다. 요약 텍스트만으로 모든 상태를 대체하지 않는다. 실제 상태 필드는 작품별로 정의한다.
3. 검증된 출력 블록 계약을 추가한다. 예: 서술, 캐릭터 대사, 승인된 이미지 참조, 선택적 상태 변화. 이미지 문자열을 출력하라는 설정만으로 저장·렌더링이 연결되지 않는다.
4. `<img="karina_emotion_...">`를 지원한다면 서버가 등록 자산으로 해석한다. 원문 HTML을 브라우저에 직접 실행하지 않는다. 누락 시에는 텍스트와 기본 이미지 등 명시적인 표시 정책을 적용한다.
5. 다인물 장면과 답변 대상을 구분한다. 현재 선택한 한 캐릭터 답변은 유지하고, 필요하면 별도 세계관 진행 모드에서 화자별 블록을 추가한다. 모든 NPC를 매 턴 별도 LLM 호출하는 방식부터 시작하지 않는다.
6. 메시지 수정/되돌리기/리롤과 상태 변경을 함께 정의한다. 상태 이벤트에 메시지/턴과 revision을 연결하고 성공한 생성에만 적용한다. 실패·중복 요청·stale 답변은 상태를 변경하지 않는다.
7. 실제 토크나이저 또는 공급자별 합리적 계수로 문맥 산정을 개선한다. 현재 prompt의 추정치는 UTF-8 바이트 합계라 대형 카드가 보수적으로 거절될 수 있다.

현재 시스템 템플릿만 system 역할을 사용하고 캐릭터/로어/기억은 user 참조 JSON으로 전달한다. 외부 카드의 system_prompt나 post_history_instructions를 서비스 system 규칙으로 승격하지 않는다. 필요한 서술/이미지 기능은 검토된 서비스 계약으로 구현한다.

## 8. 가져오기와 모듈 경계

가져오기는 분석과 확정 저장을 나눈다. 분석 결과에는 지원/변환/보류 항목, 파일 수와 예상 용량, 원본→내부 ID 매핑 계획을 포함한다. 확정은 기존 product/character/lorebook 공개 service와 types를 호출하는 상위 workflow로 조율한다. 다른 모듈 repository/ORM에 직접 접근하지 않는다.

ZIP 파일 경로 탈출, 압축 해제 크기/개수, 선언 자산과 실제 파일 불일치를 검사한다. `backgroundHTML`과 module.risum은 실행하지 않고 원본 호환 데이터로 보관하거나 보류한다. 현재 검사되지 않은 module.risum을 무시하면서 “완전 호환”이라고 표시하지 않는다.

DB 기록과 외부 파일 저장은 하나의 원자적 트랜잭션으로 간주하지 않는다. 기존 미디어 예약·완료·복구 계약을 활용해 중단 후 재개와 실패 자산 정리를 설계한다. 동일 파일 재가져오기와 의도적인 작품 복제도 구분한다.

파일에 학생 설정과 성인용 이미지 명령/자산명이 함께 포함되어 있으므로, 구조 분석 결과와 실제 게시 가능한 콘텐츠는 별도 검토해야 한다. 분석은 해당 내용을 재현하거나 실행하지 않았다.

## 9. 추천 구현 순서와 검증

| 순서 | 작업 | 완료 조건 |
|---|---|---|
| 1 | 제작 화면 + 기존 CRUD/구성/발행 연결 | 작은 작품을 직접 만들고 실제 채팅까지 연결 |
| 2 | 시작별 도입 + 대화 옵션 | 같은 작품의 장면/옵션을 바꿔도 다른 대화에 영향 없음 |
| 3 | 로어 예산/순서/스캔/조건 + 진단 | 활성/제외 이유를 설명하고 문맥 제한 안에 답변 생성 |
| 4 | 이미지 매핑과 출력 렌더러 | 승인 자산만 표시, 미등록 명령과 잘못된 출력 처리 |
| 5 | CHARX 분석·매핑·선택 가져오기 | 원본 미지원 항목을 보여주고 재시도 가능한 초안 생성 |
| 6 | 상태 이벤트·다인물 진행 | 재시도/리롤/되돌리기/버전 전환 후 상태 일관성 |

최소 버전은 RisuAI 없이 직접 작성한 작은 작품으로 검증한다. 전체 파일 가져오기 전에 카리나 프로필·소수의 비성적 이미지·세계관 항목·시작 장면 하나로 매핑 품질을 확인한다.

구현 후 필요한 검증: 기존 API/발행 스냅샷 회귀, 최초 시작 보존, 조건 선택과 상호 배타, 로어 예산과 순서, 미등록 이미지, 가져오기 중단/재개, 중복 생성의 상태 불변, 메시지 수정/되돌리기 시 상태 복구. 이번 작업은 정적 분석이며 실행 테스트나 RisuAI 호환 실행 검증은 하지 않았다.

## 11. 키워드 활성화 보조 설정 재확인

일반 항목 57개 중 비어 있지 않은 키워드가 있는 항목은 20개다. 이 중 13개는 constant=false이고, 나머지 7개는 constant=true여서 키워드가 있어도 상시 포함 설정이다. 일반 항목 전체에서는 constant=true가 16개, 빈 키워드이며 constant=false가 28개다.

키워드에는 한글/영문, 이름/성, 표기 변형과 관련 개념이 함께 등록되어 있다. 예를 들어 루나 항목에는 Luna, Lovegood, 루나, 러브굿, 래번클로, Ravenclaw가 들어 있다. 비상시 키워드 항목 13개는 모두 enabled=true, case_sensitive=false, use_regex=false, selective=false다.

책 설정은 scan_depth=9, risu_fullWordMatching=false, recursive_scanning=false다. 최근 문맥 스캔과 완전 단어 일치 완화에 해당하는 설정이 들어 있으나, 실제 스캔 단위와 매칭 세부 동작은 실행 엔진에서 검증해야 한다. 키워드 자동 확장이나 의미 검색을 수행하는 별도 보조기는 card.json에서 확인하지 못했다.

risu_activationPercent는 11개 항목 모두 null, risu_loreCache는 12개 항목 모두 null이다. 필드가 있다는 이유만으로 확률 활성화나 캐시 보조가 동작한다고 볼 수 없다. 이벤트 본문의 roll 매크로도 그 항목 자체를 활성화하는 키워드 조건과는 구분한다. module.risum 내부에 추가 보조 기능이 있는지는 미확인이다.
