## 1. 이번 조사에서 확인한 범위

캐릭터 채팅을 구성하는 정보는 인물 설정, 유저의 역할, 세계관, 시작 상황, 대화 중 변화, 화면에 표시할 파일로 나누어 보는 것이 유용하다. 이 구분을 데이터와 실행 흐름에 반영하는 방향을 제안한다. 각 개념마다 독립 테이블이 반드시 필요하다는 뜻은 아니다.

**이 문서는 아카라이브 글을 읽고 요약한 보고서가 아니다.** 요청된 게시판은 웹 도구에서 열리지 않았고, 브라우저 접근도 사이트 안전 정책으로 거부되었다. 차단 이후 다른 경로로 해당 사이트 본문을 수집하지 않았다. 공식 프로젝트 문서·코드·형식 명세를 독립적으로 조사하고, 확보하지 못한 커뮤니티 자료를 아래에 기록했다.

확인한 외부 자료는 14개 페이지다. 이 중 13개는 관련 텍스트를 읽었고, RisuAI Prompt Template 페이지 1개는 제목·수정일과 이미지 중심 구성까지만 확인했다. 일부 긴 문서는 이번 주제에 해당하는 구간을 읽었다. 전체 구현·전체 명세 준수 여부를 검증한 것은 아니다.

### 증거 구분

| 표시 | 의미 | 해석 범위 |
| --- | --- | --- |
| 공식 문서 | 프로젝트가 관리하는 사용 문서·위키 | 해당 도구가 설명하는 기능. 오래된 위키는 현재 배포판 보증으로 보지 않음 |

| 설계 제안 | 위 자료와 프로젝트 목적을 종합한 판단 | 외부 도구의 필수 규칙이나 확정된 제품 요구사항이 아님 |

## 3. 개념을 프로젝트 언어로 정리

아래의 ‘우리 앱에서의 책임’과 예시는 설계 제안이다. 외부 제품이 같은 DB 구조를 사용한다는 주장이 아니다.

| 개념 | 의미 | 우리 앱에서의 책임 | 예시 |
| --- | --- | --- | --- |
| 캐릭터 | AI가 연기하는 등장인물 | 인물 설정과 기본 표현 자산 | 사서 하린의 성격·말투·평상복 이미지 |
| 유저 페르소나 | 사용자가 그 대화에서 연기하는 역할 | 계정과 분리한 역할 프로필 | 같은 계정의 ‘신입생 민’과 ‘교수 윤’ |
| 로어북 | 조건에 따라 참조할 설정집 | 내용·활성화 규칙·삽입 정책 | 도서관 규칙, 왕국 역사, 인물 관계 |
| 장소 | 공간에 대한 정적 설정 | 초기에는 `location` 로어 엔트리 | 북쪽 도서관의 외관·출입 조건 |
| 시나리오 | 시작 상황과 진행의 전제 | 상품의 실행 설정 또는 별도 시나리오 정의 | 폭우로 도서관에 갇힌 첫날 |
| 대화 상태 | 이번 대화에서 현재 참인 상태 | 세션에 저장하고 턴에 따라 갱신 | 현재 장소, 문이 잠김, 사건 단계 |
| 메모리 | 실제 진행된 대화에서 얻은 기억 | 출처와 유효 범위가 있는 요약·사실·사건 | 어제 하린에게 열쇠를 맡김 |
| 미디어 에셋 | 화면/소리에 사용할 파일 | 저장·권한·참조·선택·표시 | 캐릭터 표정, 장소 배경, 효과음, 유저 아바타 |
| 프리셋 | 정보를 모델에 보내는 구성 정책 | 순서·역할·토큰 예산·생성 옵션 | 로어는 기록 앞, 작가 노트는 최근 발화 근처 |
| 카드/패키지 | 여러 설정과 파일의 교환 단위 | 가져오기·매핑·내보내기 | CCv2 JSON/PNG, CCv3 CHARX |

캐릭터와 유저 페르소나를 구별하는 근거는 [S07 Personas](https://docs.sillytavern.app/usage/core-concepts/personas/)이며, 시나리오·첫 메시지·제작자 메모의 구별은 [S06 Character Design](https://docs.sillytavern.app/usage/core-concepts/characterdesign/)에서 확인했다.

### ‘에셋이 많다’가 의미하는 것

`image/audio/video`는 파일의 매체 종류이고, `avatar/expression/background/bgm`은 사용 목적이다. 캐릭터·장소·시나리오·페르소나는 그 파일이 연결되는 대상이다. 세 축을 나누면 도메인마다 파일 보관 기능을 새로 만들 필요가 줄어든다. 이는 [S13 CCv3의 에셋 구분](https://github.com/kwaroran/character-card-spec-v3/blob/main/SPEC_V3.md)을 참고한 **우리 앱의 설계 판단**이다.

파일을 보관하는 것만으로 상황에 맞는 그림이 나타나지는 않는다. 언제 어떤 그림을 선택할지, 메시지 속 참조를 어떻게 해석할지, 화면 어디에 표시할지를 정해야 한다. [S09 Character Expressions](https://docs.sillytavern.app/extensions/expression-images/)는 그중 감정 분류와 표정 표시의 사례다.

제안: 화면 표시용 파일과 모델 입력에 보낼 이미지를 별도로 취급한다. 배경 이미지 전체를 매 턴 모델에 보낼 필요는 없으며, 필요한 경우 장소 설명이나 허용된 에셋 키를 프롬프트에 넣는다. 이미지 이해가 제품 요구사항일 때만 멀티모달 입력을 추가한다.

### ‘로어북이 활성화된다’의 두 단계

1. 키워드·상시 적용·기타 조건을 만족해 **후보**가 된다.
2. 사용 범위·예산·중복·삽입 위치 정책을 통과해 **최종 프롬프트에 포함**된다.

SillyTavern은 전체 로어 예산이 소진되면 키워드가 맞아도 추가 활성화를 중단하며 상시 엔트리를 먼저 고려한다. 검색 깊이와 추가 검색 대상도 설정할 수 있다. 이 동작을 바탕으로 우리 앱에서도 후보 선택과 최종 조립을 분리할 것을 제안한다. [S08 World Info](https://docs.sillytavern.app/usage/core-concepts/worldinfo/)

### 장소 설정과 현재 장소의 차이

‘북쪽 도서관에는 지하 서고가 있다’는 정적 로어다. ‘이번 턴에 지하 서고로 이동했다’는 대화 상태 또는 사건이다. 같은 공간을 설명하는 정보라도 저장 수명과 갱신 주체가 다르다.

**설계 예시:** ‘도서관’이라는 단어를 회상했다고 현재 배경을 도서관으로 바꾸면 오작동한다. 초기에는 배경을 수동 선택하고, 자동 이동이 필요해지면 명시적인 상태 변경 이벤트를 도입한다. 단순 키워드 활성화를 이동 판정으로 사용하지 않는다.

### 유저 정보의 세 가지 범위

| 정보 | 권장 위치 | 기본 공유 범위 |
| --- | --- | --- |
| 로그인 계정의 이름·설정 | identity | 계정 |
| 이번 역할극에서의 이름·외형·직업 | persona | 선택된 페르소나와 해당 대화 |
| 이번 대화에서 생긴 약속·관계 변화 | memory | 해당 대화 |

위 범위는 프로젝트 제안이다. 역할극 속 직업이나 관계를 계정 전체의 사실로 자동 승격하지 않는다. 계정 간·대화 간 장기 기억 공유는 별도 선택 기능으로 남긴다.

## 4. 추가로 설계에 반영할 정보

| 주제 | 확인한 사실 또는 제안 | 프로젝트에 주는 영향 |
| --- | --- | --- |
| 제작자 메모와 작가 노트 | CCv2 `creator_notes`는 프롬프트에 쓰지 않는 필드다. [S12](https://github.com/malfoyslastname/character-card-spec-v2/blob/main/spec_v2.md) | 현재 로어 타입 `author_note`와 구분해 매핑해야 함 |
| 컨텍스트 예산 | 설정·시나리오도 컨텍스트를 차지한다. [S06](https://docs.sillytavern.app/usage/core-concepts/characterdesign/) | 에셋 수보다 실제로 주입되는 텍스트·메시지 토큰량을 먼저 측정 |
| 요약의 정정 | 요약은 손실·오류가 있을 수 있고 수정·복원 흐름을 제공한다. [S11](https://docs.sillytavern.app/extensions/summarize/) | 원문 참조와 버전, 수동 정정, 재생성 시 무효화 규칙 필요 |
| 파일 규약과 실행 지원 | CCv3가 다양한 파일을 담을 수 있어도 앱의 전 기능 지원을 요구하는 것은 아니다. [S13](https://github.com/kwaroran/character-card-spec-v3/blob/main/SPEC_V3.md) | 이미지부터 지원하고 고급 파일은 보존/미지원 상태를 알리는 방식 가능 |
| 설정의 주입 위치 | 프롬프트 구성과 순서는 별도 관리 대상이다. [S10](https://docs.sillytavern.app/usage/prompts/prompt-manager/) | DB 컬럼 추가 외에 조립기와 프롬프트 미리보기가 필요 |
| 로어의 소유와 사용처 | RisuAI 소스는 캐릭터·채팅·모듈 로어를 결합한다. [S03](https://raw.githubusercontent.com/kwaroran/RisuAI/main/src/ts/process/lorebook.svelte.ts) | 소유자와 적용 대상을 별도 관계로 모델링할 이유가 있음 |
| 호환되지 않는 정규식 | 로컬 코드는 Rust 기반 정규식을 사용하고 ST 문서는 JavaScript 문법을 설명함 | 가져오기 때 문법 검증·변환 가능 여부와 경고를 제공해야 함 |

보고서에서 제안하는 스냅샷 보존, 파일 수명 관리, 재시도, 대화 상태, 모듈 경계는 위 공식 자료를 참고해 현재 서버형 프로젝트에 맞게 도출한 설계다. 외부 제품의 기능을 전부 복제해야 한다는 결론은 아니다.

## 5. 남은 조사와 확정할 수 없는 것

- 아카라이브 공지/정보 모음의 실제 링크 목록과 갱신일, 정보 탭 개념글 여부, 본문, 댓글의 정정 사항.
- 커뮤니티 카드·모듈 샘플에서 캐릭터/장소/시나리오/유저 에셋이 실제로 어떤 문법과 규칙으로 호출되는지.
- 특정 RisuAI·SillyTavern 배포판의 지원 범위. 이번에는 해당 앱을 설치하거나 실제 카드를 실행하지 않았다.
- 페르소나 에셋 팩 공유와 일반 유저 아바타의 사용 비중. 공식 규약에 필드가 있다는 사실만으로 수요를 확정하지 않았다.
- 키워드, 요약, 벡터 검색의 한국어 역할극 품질. 모델 비교 실험 없이 최적 임계값이나 순위를 제시하지 않았다.

미확인 커뮤니티 정보 때문에 전체 코드 분석을 보류할 필요는 없다. 다만 특정 에셋 문법·스크립트 런타임·완전한 외부 카드 호환성은 실제 대상 자료 확보 후 확정하는 것이 적절하다.
